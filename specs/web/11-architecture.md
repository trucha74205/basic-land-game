# Web app: architecture

## Packages (npm workspaces monorepo)

```
blg/
  engine/   pure rules engine (exists)
  server/   Fastify HTTP + WebSocket, SQLite, Scryfall proxy, Web Push
  web/      React + Vite PWA
  deploy/   Dockerfile, docker-compose.yml, nginx example, env example
  specs/
```

Dependencies point inwards only: `web -> engine` (types and view helpers, no game logic), `server -> engine`. The engine knows nothing about either.

## Stack

| Concern | Choice |
|---|---|
| Server | Node 22, Fastify 5, `@fastify/websocket`, `@fastify/static`, `@fastify/rate-limit` |
| Validation | `zod` schemas for every REST body and WebSocket message |
| Persistence | SQLite via `better-sqlite3` (12.x; 11.x does not build on Node 26 used for development), WAL mode |
| Push | `web-push` with VAPID keys |
| Client | React 19 (the 8bitcn components use its ref-as-prop style), Vite, TypeScript, `react-router`, Zustand, `vite-plugin-pwa` (Workbox) |
| UI kit | Tailwind CSS, shadcn/ui and the 8bitcn/ui registry (MIT), components copied into the repo (W-90) |
| Tests | Vitest everywhere, Testing Library (web), Playwright (end to end) |

## Authority and state

- **A-01** The server is authoritative. Clients send actions; the server validates them with the engine (`applyAction` throws on illegal actions) and broadcasts results. The client never runs rules.
- **A-02** The engine seed is generated by the server and never leaves it. Clients receive only `getView` and `getEvents` output for their seat, plus the legal actions for their own decision. The raw `Game` object, libraries, opponent hand and `Game.log` are never serialized to clients.
- **A-03** Game state is the config (with seed) plus the ordered list of applied actions. The server rebuilds a `Game` by replay (`createGame` then `applyAction` for each action) and caches it in memory. Because the engine is deterministic, no other state needs saving.
- **A-04** Each game has a `version` equal to the number of applied actions. Every state message carries it.
- **A-05** Actions for one game are applied strictly in order: validation, engine call and the database write run synchronously in one Node tick, so no queue object is needed. The server runs as a single instance (no horizontal scaling needed).
- **A-06** The engine has a `RULES_VERSION` constant stored with every game. If the engine rules change in a way that breaks replay, games with an older version cannot be resumed: they are marked `abandoned` and the players are told. The engine exports `RULES_VERSION` (currently 1) and it is bumped on every rule change that alters replay results.

## Server modules

| Module | Responsibility |
|---|---|
| `games` | create/join/rematch, apply action, auto-pass scheduler, replay |
| `ws` | connections, seat authentication, presence, fan-out of filtered views |
| `store` | SQLite access and migrations |
| `scryfall` | rate-limited client, lazily built printing index, image cache; used only for custom art (`13-images.md`) |
| `push` | subscriptions, notification decisions (`14-notifications.md`) |
| `cleanup` | retention jobs |

## Database (SQLite)

```
games(id, code, status, config_json, rules_version, version, next_game_id, created_at, updated_at, finished_at)
seats(game_id, seat, token_hash, nickname, art_json, owner_id NULL, last_seen_at)
actions(game_id, idx, action_json, created_at)          -- append-only, PRIMARY KEY (game_id, idx)
push_subscriptions(id, game_id, seat, endpoint UNIQUE, p256dh, auth, created_at)
rematch_votes(game_id, seat)
printings(scryfall_id, land_type, set_code, set_name, artist, collector_number, released_at, image_json, fetched_at)
image_access(path, bytes, accessed_at)                  -- image cache bookkeeping (I-15)
```

`next_game_id` links a finished game to its rematch (W-40). The rematch game reuses the seat token hashes, so a player's token works in the new game.

`status`: `waiting`, `active`, `finished`, `cancelled`, `abandoned`.

Retention (configurable): finished or cancelled games deleted after 30 days, waiting or idle active games after 14 days, together with their actions and push subscriptions.

## Client modules

`components/ui/8bit` (copied 8bitcn components), `components/game` (tiles, hand, stack, dialogs), `api` (REST), `socket` (WebSocket with automatic reconnect and backoff), `store` (Zustand: snapshot, legal actions, UI state), `ui` (screens and components), `sw` (service worker: precache, runtime cache for `/img/*`, push handlers), `i18n`, `cues` (sound, vibration, title).

## Security

- **S-01** No cookies and no ambient credentials. The seat token goes in the first WebSocket message (`hello`) or an `Authorization: Bearer` header for REST, so CSRF is not applicable.
- **S-02** WebSocket upgrade checks the `Origin` header against `PUBLIC_URL`.
- **S-03** Rate limits: game creation and joining per IP, message rate per connection, 4 KB maximum message size, 16 KB maximum REST body. Limits are applied in nginx and again in the app (`trustProxy` enabled for the nginx hop only).
- **S-04** Invite codes are 8 characters of Crockford base32 (40 bits) and single-use for seat 1; guesses are rate limited.
- **S-05** The image proxy only serves UUIDs that exist in the `printings` table and only fetches from `cards.scryfall.io` (no open proxy, no SSRF).
- **S-06** Security headers (CSP without inline scripts, `X-Content-Type-Options`, `Referrer-Policy: no-referrer`, `frame-ancestors 'none'`) set by the app.
- **S-07** The container runs as a non-root user with a read-only root filesystem and one writable volume.
- **S-08** Nicknames are rendered as text only, never as HTML.

## Testing strategy

- Server: unit tests against in-memory SQLite and the real engine; WebSocket integration tests with two `ws` clients; Scryfall client tests with a mocked `fetch` (no live calls in CI).
- Web: component tests for table states derived from fixtures; protocol client tests with a fake socket.
- End to end (Playwright): two browser contexts play a game; one goes offline and rejoins; mobile viewport at 360x640; server restart mid-game.
- Every Gherkin scenario in `features/web-*.feature` maps to at least one test, tagged with the requirement ID.
